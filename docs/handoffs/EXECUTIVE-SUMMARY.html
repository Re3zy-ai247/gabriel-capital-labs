  2. Adversarial gate — NOT READY.   3. Founder ruling. Keep the prepaid Wallet and the authorize-hold → settle-at-provider-acceptance model; commission a bounded refinement, not a redesign (COMMITMENT-REFINEMENT-BRIEF.md).
  4. Refinement cycle 1 (W1–W3). Built the commitment model: a real serialization anchor lock, per-letter/attempt-scoped settlement grain, the payer-principal model, the Fulfillment Recovery Engine, and the FINAL REVIEW interface. Merged in COMMITMENT-RESOLUTION.md (original).
  5. Re-gate, cycle 1 — NOT READY.   6. Refinement cycle 2 (pre-decided rulings). REFINEMENT-2-DIRECTIVE.md pre-decided four cross-document rulings: unified attempt lifecycle; one canonical claim-key registry; provider acceptance is irreversible (post-acceptance remediation is accounting-only); FINAL REVIEW sits after the hold, before Submit, bound to a server-issued token.

The two decisions only the Founder can make

These are hard preconditions, not softened by the READY-WITH-DISCLOSURES verdict. No Wallet implementation work should start before both are addressed.

1 · CROA §404 advance-fee counsel question (CRITICAL, unresolved). The prepaid Wallet is, on the review's own analysis, the most legally adverse charging shape available: money received at top-up — potentially weeks before any package exists — and captured at provider acceptance, before printing. Keeping the Wallet does not moot this question. Every refinement document carries the identical header note: settlement-at-acceptance is stronger than capture-at-top-up but "does NOT moot the counsel question — funds are still received in advance at top-up... the hard precondition before any wallet implementation phase." The six-part counsel question, including the named compliant alternative (Stripe manual-capture: authorize at Approval, capture at Delivered / Return-Receipt-Archived), is in ADVERSARIAL-REVIEW.md §3.4.
2 · Gate D Phase −1 (CRITICAL, unresolved). Every new migration this program proposes (Case, DisputePackage, DisputePackageLetter, Claim, WalletLedger) is blocked by ratified canon: Gate D has never executed, production carries no _prisma_migrations history, and the schema-safety preflight rejects a seventh migration directory outright. A Phase −1 must precede any Phase 1 migration work (ADVERSARIAL-REVIEW.md F1) — unchanged through every refinement cycle.

The three headline residual disclosures

  1. The vendor-confirmation question set (11 questions, unanswered). LetterStream's actual cancellation window is not in the repository and has never been asked. Until answered, the architecture assumes the worst case everywhere, including operator-facing warning copy. Full list: FULFILLMENT-COMMITMENT-BOUNDARY.md §2.1–§2.2 (the same 11 questions apply independently to every future adapter).
  2. The §611-clock-without-a-receipt question (counsel/CCO-pending). The clock now anchors at a single point, RETURN_RECEIPT_ARCHIVED (correcting a three-way legal conflict). Whether DELIVERED alone, absent an actual receipt artifact, may ever start that clock is named for counsel/CCO, not resolved by fiat (COMMITMENT-RESOLUTION.md §1 F8; RECOVERY-ENGINE.md §4 scenario 11).
  3. Implementation-discipline dependency. Every "eliminated" verdict (the overdraft lock, the free-fulfillment closure, the partial-settlement grain) is a property of the specified guard contracts, not of the architecture in the abstract — COMMITMENT-RESOLUTION.md states these mechanisms "eliminate defects only if built as specified." This is why docs/handoffs/NEXT-SPRINT.html recommends design-only conformance-test work before implementation.
