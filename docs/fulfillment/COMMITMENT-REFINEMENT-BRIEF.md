2. Transaction model: balance exists → Approve → **Authorization Hold (not deduction)** → CreditVector validation → Submit → **Vendor accepts → Permanent Settlement** → production → mail. Vendor rejects → **hold released, balance restored, Kai explains**. Nothing is silently consumed.
3. Explicit irreversible-confirmation UX before submission (FINAL REVIEW copy skeleton provided by the Founder — architect the interaction).
4. Kai never says "Failed" and never exposes raw vendor errors — translation only.

## Program Director spine (pre-decided mechanics — all agents build on THIS; deviations must be argued in-doc, not silent)

S1. **Serialization anchor (resolves F3).** New additive `Wallet` table: one row per **payer principal**, holding NO balance — a lock anchor (`id`, `principalType consumer|agency`, `principalId`, `createdAt`, optional `lockVersion`). Every money-moving operation runs in one transaction: `SELECT … FOR UPDATE` on the anchor row → fold the ledger → verify invariant (available = fold(settled+active-holds) ≥ requested) → insert ledger row(s) → commit. The prior INSERT…SELECT "guard" is retracted (it takes no lock; the "structurally impossible" claim was false). Balance remains derived-by-fold; the accounting fold has NO zero-floor (deficits representable); any floor is display-only.

S2. **Entry vocabulary + key (resolves F4, F5, F9-iii).** Entry kinds: `fund` (top-up, +), `authorize` (hold, −available, not −settled), `settle` (converts a hold permanent, at provider acceptance), `release` (restores a hold), `clawback` (−, chargeback/refund-reversal; may drive fold negative), `adjust` (owner-gated compensating correction, ±). Settlement grain is **per-letter**: `subjectId` = the manifest id (`mail_<letterId>`), with `attempt Int` (generation) in the key: `@@unique([walletId, subjectId, entryKind, attempt])`. A package-level authorization = the SET of per-letter holds created atomically inside one anchor-locked transaction (all-or-nothing hold creation; package `authorizationGroupId` ties them). Consequences: partial fulfillment settles per accepted letter and releases per rejected letter (F5 dissolved); re-authorization after release is `attempt+1` (F4's structural impossibility dissolved); retry claims are attempt-scoped (F9-iii dissolved). Guards inside the locked txn: `settle` requires an ACTIVE hold (authorize present, no settle/release) for (subject, attempt); `release` likewise; `settle` after `release` refuses (consume-after-void closed); double-settle refuses via the unique key.

S3. **Funding integrity (resolves F6).** Top-up credits `checkout_session.amount_total` (captured amount) — never metadata; `allow_promotion_codes: false` on wallet top-ups; webhook grant deduped via the existing 3-state Stripe claim ledger keyed `<eventId>:wallet_topup`. `charge.refunded`/`charge.dispute.created` on consumed funds → `clawback` entry (fold may go negative → wallet enters `deficit` posture: no new authorizations until cured; operator surface + Kai explanation; cure = fund or owner `adjust`).

S4. **Payer principal model (resolves F7).** The wallet belongs to a payer principal: consumers fund their own; **agencies fund an agency wallet that pays for managed-client fulfillment** (mirrors the ratified entitlement law "the agency is the payer"). Spend-authority table: consumer self → own wallet; agency owner/staff acting in a client workspace → agency wallet, audit records `actor` = the real operator identity + `onBehalfOf` = client; **admin impersonation → money actions BLOCKED** (read-only wallet view; explicit refusal copy). The MailService `actor:"user"` stamp is superseded by a principal-aware audit shape.

S5. **Two-layer commitment boundary.** (a) FINANCIAL boundary (CreditVector law): permanent settlement occurs ONLY at provider acceptance — never earlier. (b) OPERATIONAL irreversibility (vendor fact): **VENDOR CONFIRMATION REQUIRED** — LetterStream's actual cancellation window (API acceptance vs payment vs print queue vs printing vs USPS handoff) is not in the repository and MUST NOT be invented. Until vendor confirmation, the architecture assumes worst case (irreversible at acceptance): the FINAL REVIEW warning states it, and post-acceptance cancellation is modeled as best-effort `cancel-requested` (outcome-dependent, never promised). The vendor question list ships as a deliverable section.

S6. **Recovery Engine (new subsystem, deterministic).** Consumes provider outcomes + policy verdicts + reconciliation sweeps; owns: failure taxonomy (all 17 Founder scenarios), correction workflow (rejected letter → package preserved, defect highlighted, `attempt+1` resubmission path), cancellation rules (pre-submission free; pre-acceptance = release; post-acceptance = best-effort per S5), **reconciliation sweep** (active holds past `staleAfter` → query provider status → settle/release per truth; NEVER silent expiry: authorization expiration = `release` + notification + Kai explanation; a hold never converts to settlement by timeout), off-machine `attention` flag for unknown provider statuses (adopting the gate's alternative — no illegal backward transitions in the shipped FORWARD table), operator notifications (in-app surfaces per ADR-0027 posture), and the Kai translation catalog. Like the Policy Engine: pure decision core, zero AI, every verdict carries `basis`.

S7. **CROA posture (unchanged, explicit).** Settlement-at-acceptance strengthens the §1679b(b) posture versus capture-at-top-up but does NOT moot the counsel question — funds are still received in advance at top-up. The counsel question (ADVERSARIAL-REVIEW §3.4) remains the hard precondition before any wallet implementation phase. Every refinement doc carries this note verbatim in its header. F1 (Gate D Phase −1) also stands.

S8. **Vocabulary.** authorize / settle / release / clawback / adjust; "hold", "commitment boundary", "recovery". The word "consume" is retired (ambiguity caused F4/F5).
