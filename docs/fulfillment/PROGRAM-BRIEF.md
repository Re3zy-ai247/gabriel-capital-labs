## 1. Authoritative Founder decisions (binding)

1. Operators never interact with LetterStream. LetterStream is infrastructure — **Provider Adapter #1** under the **CreditVector Fulfillment Platform**. Future adapters: LetterStream, Lob, PostGrid, Click2Mail (all five IDs already exist in `lib/mail/MailProvider.ts`).
2. Primary object: **Dispute Package** — not Letter. Primary workflow: **Case Journey** — not Mail:
   `Case → Kai Analysis → Dispute Package → Approval → Wallet Authorization → CreditVector Fulfillment → Timeline → Waiting Period → Next Recommendation`. Everything else supports the Case Journey.
3. Dispute Packages always use Certified Mail, Tracking, Electronic Return Receipt, Delivery Evidence, Immutable Timeline.
4. Operators always have two options: **Download Package** or **Send with CreditVector Fulfillment**.
5. **Fulfillment Policy Engine** — a deterministic subsystem owning: delivery policy, certified-mail enforcement, return-receipt policy, provider eligibility, wallet-authorization requirements, retry rules, idempotency, duplicate prevention, provider routing. **Kai never decides these.**
6. Wallet: architecture only. Responsibilities: authorization, fulfillment funding, marketplace, growth network, payouts, append-only ledger integration. Document integration points only.
7. Kai owns explanation, education, recommendations, narration, guided workflow. Kai never owns truth, money, fulfillment execution, or policy. Kai never exposes vendor implementation.
8. **Operational Room Constitution (constitutional PROPOSAL — package as a proposed amendment/ADR, never as ratified):** every primary CreditVector room is an operational workspace presenting current work, current state, recommended action, Kai guidance, evidence, timeline. Metrics provide context; they never replace work. The Mail Center answers "What should I do next?"
9. Package Review chain: Client → Kai Summary → Recommended Disputes → Educational Explanation → Letter Preview → PDF Preview → Approve → Download → Send with CreditVector Fulfillment.
10. Fulfillment timeline (canonical operator-visible stages): Prepared → Approved → Wallet Authorized → Submitted → Accepted → Printing → Mailed → USPS Accepted → Delivered → Return Receipt Archived → Waiting Period → Ready for Next Review.

## 2. Repository truth digest (scout-verified; do not contradict, do not re-derive)

### 2.1 The existing fulfillment spine (`lib/mail/*` — evolve THIS, never a parallel system)
- `MailManifest`: self-heal raw-SQL table (NOT in schema.prisma), id `mail_<letterId>`, write-once identity fields enforced by `MailStore`, embedded JSONB append-only audit trail enforced by `assertAppendOnly` in `lib/mail/MailAudit.ts` (throws on shrink/rewrite/seq-order break) at the store boundary (`MailStore.saveProgress`).
- 16-state manifest machine exists; operator flow today stops at `IN_REVIEW → APPROVED → PAID → QUEUED`; `MailService.dispatch()` has ZERO callers. Provider stages render as hardcoded placeholders ("Available after live mail integration").
- `MailProviderId = "letterstream" | "lob" | "postgrid" | "click2mail" | "postalmethods"`; `DEFAULT_PROVIDER="letterstream"` via `MAIL_PROVIDER` env. `LetterStreamProvider`: fully interface-conformant, rate card (base 92¢, +12¢/page, +495¢ certified, −20¢ standard), `isLive()` = `MAIL_LIVE === "true"` read per-call, and even live every method throws `MailProviderError("not_wired")` before any network call. Other four providers throw `not_implemented`. `deliverable:true` is fabricated from a ZIP regex (`LetterStreamProvider.ts:76`) — no CASS/USPS validation exists.
- Send wizard `app/mail/send/[letterId]/page.tsx`: 3 steps (Review & approve → Confirm ["Live mailing isn't switched on yet… no card charged"] → Queued), resumable from server status; APIs `POST /api/mail/prepare`, `/api/mail/:id/approve`, `/api/mail/:id/confirm` (campaign-attach gate via `lib/campaignInput.ts`; `markPaid` records `"authorized:no-charge (MAIL_LIVE=off…)"`; `recordDecision` into DecisionRegistry), `GET /api/mail/:id`.
- Mail Center `/mail` (`app/mail/page.tsx` + `lib/mailCenter.ts` — "zero AI, zero network" deterministic projection): passive stat row, per-dispute expandable rows with 6-state health pill (`WAITING_NORMALLY|NEEDS_ATTENTION|RESPONSE_RECEIVED|READY_FOR_ROUND_2|ESCALATION_AVAILABLE|COMPLETED`), Kai-intel bullets, 12-stage timeline (6 live + 6 placeholder; corrected from an earlier 9-stage digest — see the unified doc's Brief errata). NO actions on the page itself.

### 2.2 Letters domain
- Prisma models: `Tradeline` (account; score/probability/reasons/disputeAngles; `resolved`) + `Letter` (strategy, recipientType bureau|furnisher|collector, recipientName, targetBureau, `round Int`, encrypted `body`, `status LetterStatus = DRAFT|GENERATED|PRINTED|MAILED|RESPONSE_RECEIVED|RESOLVED`, response fields, `parentLetterId String?` plain — no FK). **No Dispute/DisputeItem/Case/Round/Client model.** `Bureau` = 3-value enum. Agency clients = `User` rows with `managedByAgencyId`.
- Generation: `lib/letter.ts` procedural composition (no template files) → optional AI refine (`meteredMessage`, model env `LLM_MODEL` default claude-opus-4-8) → `applyCompliance()` (CROA regex scrubber in `lib/compliance.ts`, runs unconditionally in exactly one place) → `encryptText` → create → `recordKaiEvent("letter.generated")`. Entitlement-gated (`getEntitlement`/`canGenerateLetter` → 402 + upgrade).
- "PDF" = browser print-to-PDF of `/letters/print/[id]` (server-rendered US-Letter HTML, auto `window.print()`; identity enclosures embedded). **No PDF library exists in the dependency tree; no download endpoint exists.** Any real PDF artifact requires a Founder-approved new dependency — treat as a flagged decision, not an assumption.
- Response loop: `/api/letters/[id]/response` (paste/PDF-extract via pdf-parse) → AI `analyzeResponse` → outcome fields + `recordVerifiedOutcome`; `/api/letters/[id]/round2` escalation at `round+1` requiring logged response, refused if outcome "deleted".
- Furnisher addresses: `TradelineContact` self-heal table populated ONLY by the report parser; manual corrections are not persisted back.

### 2.3 Timeline/audit mechanisms (three carry weight today)
- `KaiEvent` (Prisma + self-heal, append-only by convention, fail-open): types incl. `letter.generated/mailed`, `response.received`, `dispute.resolved`, `mail.status`, `campaign.*`. Powers `/journey` (THE timeline, ADR-0007).
- `DecisionRegistry` (self-heal, append-only): recommendation + deterministic basis; written on every queued mail.
- Platform Event Bus (`lib/eventBus/*`, migration-first `EventEnvelope`, flag `EVENT_BUS_ENABLED` default OFF): deterministic ids `evt_sha256(tenantId|type|source|dedupeKey)`, replayed:true no-refanout, contract registry `TYPE@version` zod `.strict()` refs-only, scope authorization (self|agency|platform) server-resolved, PII structural guard, tombstone redaction (`redactedAt`, payload cleared, envelope kept). **Contracts `DISPUTE_CREATED@1`, `LETTER_GENERATED@1`, `LETTER_SENT@1` already exist with zero production callers.**

### 2.4 Financial primitives (Scout C)
- `User.letterCredits Int` — the only balance field (one-time $19/5 letters; clamp-on-race spend `spendLetterCredits`; transactionally-deduped grant `creditLetters` keyed `<eventId>:letters_5`).
