# Architecture Decisions — CreditVector Fulfillment Engine v1.0

The durable design decisions this program produced, independent of which refinement cycle last touched them. Every decision is `PROPOSED` — none is ratified, none is implemented. Full detail lives in the cited `docs/fulfillment/` documents; this table is the index, not a replacement.

## Durable decisions

| # | Decision | What it is | Status | Primary source |
|---|---|---|---|---|
| 1 | **Dispute Package / Case domain** | Two new, thin, migration-backed Prisma models: `Case` (durable identity for one dispute target's whole history) and `DisputePackage` + `DisputePackageLetter` (the primary object — N letters per package, `stage` rolled up at the least-progressed constituent manifest). `DisputePackage.campaignId` ships as a plain unenforced `String` (`Campaign` is self-heal, cannot carry a real Prisma FK). `DisputePackageLetter.letterId` is `onDelete: Restrict` — a deliberate behavior change (packaged letters become undeletable). | PROPOSED, additive migration, FOUNDER-GATE (Gate D Phase −1 precondition) | `A-DOMAIN-MODEL.md`; ADR-0041 |
| 2 | **Deterministic Policy Engine** | A pure, server-only module owning delivery policy, certified-mail enforcement (a constant, never a computation), provider eligibility/routing, wallet-authorization requirements, retry scheduling, and duplicate prevention. Six laws, most importantly: fail-closed on unknowns, no decision ever originates from Kai or client input, every decision carries a `basis`, the engine never touches a provider or the network. The fourth instance of a pattern already proven three times in the codebase (`CampaignPolicy.ts`, `pickRecommendation`'s `basis` law, `planForPrice()`'s fail-closed law). | PROPOSED, code-only (no schema) | `A-POLICY-ENGINE.md`; ADR-0042 |
| 3 | **Provider abstraction + Vendor Opacity law** | Formalizes the existing `MailProvider` interface (LetterStream = Adapter #1 of five registered IDs) — not a redesign. Adds: an honest `validateAddress` contract (`deliverable: undefined` until a real CASS/USPS check exists, never inferred from a ZIP regex); a Vendor Opacity law (a response-boundary DTO strips `MailReceipt.provider`, audit strings use neutral phrasing, a static regex guard catches any vendor name reaching an operator-facing module); fail-closed status mapping (`UNKNOWN_PROVIDER_STATUS`, never a silent forward-progress fallback). | PROPOSED, code-only for the mapping fix; CASS/USPS live validation is a separate FOUNDER-GATE | `A-PROVIDER-ABSTRACTION.md`; ADR-0043 |
| 4 | **Prepaid Wallet — authorization ≠ settlement** | The Wallet remains the product direction (Founder ruling). A `Wallet` anchor row (one per payer principal, no balance, a pure lock target) makes every money-moving operation a real `SELECT … FOR UPDATE`-serialized transaction. Balance is always derived by fold, never stored, and the fold carries no zero-floor (deficits are representable and curable, not hidden). Four entry kinds survive: `fund` / `authorize` / `settle` / `release`, plus `clawback` and `adjust` for post-settlement corrections. `consume`, `void`, and `refund` are retired names. | PROPOSED, additive migration, FOUNDER-GATE (CROA counsel + Gate D preconditions) | `WALLET-COMMITMENT-MODEL.md` (supersedes `C-WALLET-INTEGRATION.md` and ADR-0044 selectively); ADR-0044 |
| 5 | **Anchor-lock serialization** | The concrete fix for the overdraft defect (F3): every authorize/settle/release/clawback/adjust operation takes a real row lock on the payer's `Wallet` anchor before folding the ledger and verifying the invariant, closing the "atomic insert guard takes no lock" defect the first gate found. Disclosed cost: one row per payer is acceptable at launch scale; must be measured before Marketplace fan-out. | PROPOSED | `WALLET-COMMITMENT-MODEL.md` §4, §7 |
| 6 | **Per-letter / attempt-scoped settlement grain** | Settlement fires per letter (`subjectId = mail_<letterId>`), not per package — dissolving the partial-package money hole (F5): a 3-letter package with 2 accepted and 1 rejected settles 2 holds and releases 1, with no invented "partial" entry kind. Every hold additionally carries an `attempt` integer; once an attempt's hold is resolved (settled or released), that attempt is **terminal forever** — the direct, permanent closure of the free-fulfillment defect (F4). Re-authorization after any release always mints `attempt+1`; there is no "same-attempt re-authorization." | PROPOSED — the F4 closure is the single most re-verified mechanism in the program (re-gate cycle 1 found it broken across a document seam; refinement cycle 2's Ruling 1 closed it; re-gate cycle 2 confirmed the closure with a traced proof) | `FULFILLMENT-COMMITMENT-BOUNDARY.md` §3; `WALLET-COMMITMENT-MODEL.md` §12 invariant 8 |
| 7 | **Unified claim ledger** | One shared, `domain`-tagged `Claim` table (`ClaimDomain: MAIL_TRANSITION \| WALLET`) rather than two independently-proposed, structurally-identical tables — the concrete stand-in for ADR-0028's dormant `IdempotencyStore` kernel port. One canonical key registry, cited (never re-derived) by every consuming document: `wallet:<subjectId>:<attempt>:<entryKind>` and `mail:<subjectId>:<attempt>:<toStage>`. | PROPOSED, additive migration | `CREDITVECTOR-FULFILLMENT-ENGINE-V1.md` §5.3; ADR-0045 |
| 8 | **Fulfillment Recovery Engine** | A new deterministic subsystem (Founder ruling #5) answering one question: something already happened — a provider outcome, a sync result, a sweep tick, an operator action — what state does the system land in, what happens to money, what does the operator/consumer see? Zero AI, zero network in the core. Owns the 17 Founder-named failure/recovery scenarios (plus a re-gate-added 18th: acceptance arriving after a hold was already released) as one deterministic matrix: scenario → detecting signal → state → wallet effect → recovery workflow → notification → Kai copy class → audit entries. Every wallet effect is one of exactly five kinds (`hold_released` / `settled` / `none` / `clawback` / `adjust`) or explicitly `founder_gate_pending` — no ad hoc sixth outcome. | PROPOSED, new subsystem | `RECOVERY-ENGINE.md`; companion `FULFILLMENT-COMMITMENT-BOUNDARY.md` |
| 9 | **Payer-principal model** | Money moves against the `Wallet` of whoever is financially responsible (consumer self, or an agency paying for a managed client's fulfillment), stamped with the real acting operator's identity — never a generic `"user"` placeholder. Admin impersonation is money-**blocked** (read-only wallet view). Where no human operator exists at all (a webhook, a reconciliation sweep), the audit trail records an honest `actorKind:"system"` rather than fabricating one. | PROPOSED — residual: agency-staff sub-identity granularity remains coarse pending the dormant Operator Identity system | `WALLET-COMMITMENT-MODEL.md` §9 |
| 10 | **Fulfillment Commitment Constitution** | The ratifiable text binding the whole program: (1) no irreversible settlement before provider acceptance — authorization is a hold, settlement converts a hold, nothing else converts anything; (2) authorization ≠ settlement (Wallet Constitution Amendment, incorporated by reference); (3) the operational irreversibility boundary is a vendor fact, not an assumption, and worst-case governs all operator language until vendor confirmation; (4) the Recovery Constitution — every failure produces a deterministic state, a preserved audit trail, a recoverable workflow, a Kai explanation; (5) Kai translates, Kai never decides. | PROPOSED constitutional text, ratification path via ADR-0041–0047 | `COMMITMENT-RESOLUTION.md` §2 |
| 11 | **Two-layer commitment boundary** | Explicitly separates what was previously conflated: Layer (a), the **financial** boundary (CreditVector's own law — settlement only at provider acceptance, ours to set, not vendor-dependent), from Layer (b), the **operational irreversibility** boundary (a LetterStream fact CreditVector does not yet know and must not invent). The two layers being merged in the original design was the direct cause of the docket #9 settlement-moment disagreement between Agents A and C. | PROPOSED | `FULFILLMENT-COMMITMENT-BOUNDARY.md` §1 |
| 12 | **Operational Room Constitution** | A proposed constitutional amendment (never self-ratifying by shipping): every primary CreditVector room presents six mandatory elements — current work, current state, one recommended action, Kai guidance, evidence, timeline — with metrics as context only, never first-on-page. The Mail Center evolution is its first proof, not a one-off UX choice. | PROPOSED, Founder ratification required | `OPERATIONAL-ROOM-CONSTITUTION-PROPOSAL.md`; ADR-0047 (pointer ADR) |
| 13 | **FINAL REVIEW — two distinct consent moments** | Approve (chain step 7: price + line items shown, triggers the reversible authorization hold) and FINAL REVIEW (immediately before Submit: the point of no return, price re-shown, four real operator assertions, bound to a server-issued single-use expiring token carrying `contentHash`/`warningVersion`/`estimatedTotalCentsShown`/`policyVersion`) are two renders, never one screen doing both jobs. | PROPOSED | `KAI-FULFILLMENT-UX.md` §1; `REFINEMENT-2-DIRECTIVE.md` Ruling 4 |
